# Runtime stability evidence

All device operations targeted the same gated disposable AVD, `emulator-5554 / HydroNudge_Pixel10a_API37`. Personal phones were not involved. The installed image identifies itself as Android 17/API 37. These findings keep the stability gate open.

1. A Hydro hot-display-resize run recorded an input-dispatch ANR at 19:36:34 on 11 November. Its app main thread was in native polling in the collected trace. This does not establish a cause. Original evidence: `evidence/hydronudge/resize-anr.txt` and `resize-anr-dropbox.txt`.
2. During the Fumipoka layout matrix, standard/small/large/tablet captures completed, then the Android activity service stopped responding during the next display/font transition. The recovered `system_server_watchdog` entry at 20:16:26 reports WindowManager/display/animation threads blocked for 73 seconds. The display thread was synchronously waiting for SurfaceComposer `captureLayersSync` while holding the WindowManager lock. Memory pressure totals showed zero current averages; CPU pressure was elevated. This identifies the observed blocking stack, not the ultimate cause or responsibility. See `evidence/system-server-watchdog.txt` and Fumipoka's `display-service-hang-*` files. System processes subsequently reported DeadSystemException.
3. Later, after Fumipoka's navigation/theme instrumentation completed successfully, the emulator process exited and ADB had no attached target. No matching recent Windows Application Error event was returned by the limited event query. The cause of that exit was not established. The next test refused to run.
4. The AVD was cold-started without deleting user data or loading/saving snapshots, using a headless SwiftShader renderer, 2048 MiB and two virtual CPU cores. Its stdout records the actual renderer and boot completion. A System UI unresponsive dialog appeared during startup/host build load; Wait was selected, and the app hierarchy became available. This is also retained as a test-environment failure, not silently retried into a clean claim.

5. At the 12 November continuation, the previous host processes were no longer running. The same AVD was cold-started without wiping data or loading/saving snapshots, with SwiftShader, 3072 MiB and four virtual cores. Retained matrix checkpoints were resumed, and the remaining configuration, document-picker, timer-recovery, native-widget and upgrade checks completed. This continuation does not establish the cause of earlier hangs or prove that the renderer or memory allocation fixed them. Startup evidence is in `evidence/emulator-20261112.stdout.log` and its metadata.

Subsequent successful checks are recorded individually by their result JSON and logs. They do not erase preceding failures, prove a renderer fix, or certify physical/OEM behavior. The full release gate still requires stable-platform stress, minimum-API and physical-device checks, background/periodic timer/reminder behavior, accessibility coverage and production-signed upgrades. Timer recovery added in this work deliberately reopens paused and does not promise an alarm or automatic completion while the process is absent.

Temporary layout/font/radio settings are manipulated only on the emulator. Matrix helpers attempt restoration even on failure; final normalized device settings are captured separately. A temporary notification grant is revoked after Hydro tests. Fixture Room snapshots and explicit restore checks preserve emulator records; no `adb clear-data`, uninstall or production reset was used.
